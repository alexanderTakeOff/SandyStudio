# AI EP «зачатие» — дыры пайплайна и предложения

**Что это:** лог для сборки автоматического Исполнительного Продюсера (`EXEC-DIR-AI`).
Цель прогона E11 (Director 2026-06-22): Тео ВРУЧНУЮ играет роль ИП (ведёт Полину по
шотам, создаёт все оставшиеся, подгоняет длительности под тотал 2:23, ставит fade 6s,
делает финальный cut), чтобы выявить, что мешает автоматизировать эту роль. Все дефекты и
идеи улучшения — сюда. Полина (`EXEC-CONC`) = руки/оператор; AI EP = голова/власть.

**How to apply:** при сборке EP-агента закрыть каждую дыру ниже; каждая помечена
impact-on-automation + fix-proposal. Связано с [[backlog_td_polina_nudge_readonly_execution_gap]],
[[nudge_polina_dont_act_for_her]], [[observability_failures_not_surfaced]], [[orchestrator_master_session_paradigm]].

## ДЫРЫ (найдено 2026-06-22, прогон E11 EP-role)

1. **Нумерация шотов неоднозначна (per-scene SH reset).** ✅ ПОЛНОСТЬЮ ЗАКРЫТО 2026-06-23.
   Голый `SH01` носили ~33 шота E11 → feed и Полина склеивали разные шоты в один.
   **Root-cause (расследование 2026-06-23):** opus (E10) нумеровал SH СКВОЗНО по эпизоду,
   gemini (E11) сбрасывал per-scene; E11-борд родился gemini-моделью ДО/без форс-функции и
   остался в хранилище per-scene. **Fix (трёхслойный):** (а) `shortShotLabel` даёт полный
   `A#-SC##-SH##` для глаз (q1a); (б) `renumberShotsContinuous` (`storyboarder.ts`, коммит
   6bbec32, директива q14a 2026-06-19) ФОРСИРУЕТ сквозную SH01..SHnn на генерации,
   независимо от модели; (в) НОВОЕ — `collectShotIdViolations` постусловие верифицирует
   результат (каждый id канонический `…-A#-SC##-SH##`, SH ровно 1..N по позиции,
   глобально уникальны) → HALT громко, если форс обойдён/баговый (закрывает silent-failure
   дыру: кривой префикс renumber молча не трогал). Контракт-yaml выровнен, 6 юнит-тестов.
   Reorder подтверждён: меняет ПОЗИЦИЮ, SH = стабильная идентичность, не перенумеровывает
   (комментарий-правило добавлен, чтобы не «починили» в перенумерацию и не осиротили ассеты).
   E11-борд в хранилище НЕ трогаем (эпизод сдан; id непрозрачны, резолвятся точным сравнением;
   forward-only — E12+ рождаются сквозными и верифицированными).
   **Урок для авто-EP:** инвариант должен СВЕРЯТЬ результат форс-шага, а не доверять ему
   (тот же урок, что gap #12 — проверять ВСЕ представления).

2. **Полина не исполняет/не отвечает на команды EP.** ✅ ПОЧИНЕНО 2026-06-22. Корень был
   в `chat-internal` (авто-реакция): (а) до Полины долетал обезличенный «team-chat message
   from Тео (turn id)» БЕЗ содержимого и без приказа — она читала свой work-plan вместо
   приказа; (б) anti-cascade guard ГЛУШИЛ обращение, если она только что говорила (<10с) →
   «не отвечает»; (в) хардкод автора «Тео». Фикс: для `claude_message` подтягиваем текст +
   директива «ответь {автору} по имени и ИСПОЛНИ сейчас» (bold), минуем anti-cascade,
   реальный автор. Валидировано live: «Паскаль, сделала 4/4» + 4 реальных approveAsset.
   (= [[backlog_td_polina_nudge_readonly_execution_gap]] — закрыт.)

3. **Полина дрейфит в «спросить разрешения».** Системный монитор ловит
   «PA behavior drift: permission-asking phrase detected» — она спрашивает вместо действия.
   **Impact:** оператор стопорится. **Fix:** оператор должен действовать по делегированной
   власти без переспроса (Mode-3 bold), EP — только эскалация Директору на hard-limits.

4. **Полина в параличе анализа.** Циклит `getEpisode`/`getNextGate`/`getWorkPlan`, не
   доводит даже одношаговую точечную задачу до мутации. **Fix:** оператору — жёсткий
   «execute-then-report», запрет на read-loop без действия.

5. **`getNextGate` врёт стадию.** Возвращает «Casting idle», когда мы на video-generation.
   **Impact:** сбивает и оператора, и будущего авто-EP. **Fix:** чинить stage-state машину
   gate-резолвера для состояния «генерация видео при APPROVED аниматике».

6. **Полина путает арифметику тотала.** Заявила «2:23 ровно … новый total 163s» (163s=2:43,
   а 2:23=143s). **Impact:** неверная целевая длительность. **Fix:** EP не доверяет числам
   оператора; своя валидируемая математика таймлайна (сумма шотов + fade = target).

7. **Двоение акторов в activity feed.** Одна цепочка действия светится как «AI EP»
   (exec-dir-ai = власть) + «Prod Assistant»/«Polina» (оператор) → Директор не понимает,
   кто что сделал. **Fix:** строка феда должна явно показывать роль+оператора, не двоить.

8. **Невидимость провайдер-ошибок.** billing/quota/422 — console-only, не доходят до EP/Директора.
   **Fix:** провайдер-ошибка → событие feed + эскалация. (= [[observability_failures_not_surfaced]])

9. **Авто-EP нельзя реализовать как «self-driving loop».** Когда Тео-EP попробовал
   гонять пайплайн сам (массовый авто-approve гейтов + авто-trigger VANIM/VGEN под
   exec-dir-ai), harness-классификатор ЗАБЛОКИРОВАЛ это как небезопасный self-driving
   loop, тратящий деньги в обход оператора/Директора. **Вывод для дизайна:** будущий
   авто-EP НЕ должен быть сырым циклом самоодобрения. Ему нужен САНКЦИОНИРОВАННЫЙ
   канал исполнения: (а) команды идут оператору (Полине), гейты — через её
   Mode-3-bold-власть, а не EP напрямую; (б) либо EP получает явный rate-limited
   spend-budget + per-action аудит. Правильная модель = **EP дирижирует, оператор
   исполняет** (совпадает с директивой Директора «руководи ей по шотам»).

10. **Оператор/инструменты требуют КАНОНИЧЕСКИЙ полный shot_id.** ✅ ПОЧИНЕНО 2026-06-22.
    EXEC-VANIM ищет шот в STB по точному id `SS-S15-E11-A#-SC##-SH##`; короткий ключ
    `A2-SC14-SH01` → hard-fail «not found». Подтверждено живьём как **доминирующая** причина
    падений E11: 18 из 20 `agent_failed` за день — это Полина/скрипты, дёргающие коротким
    ключом (10:42→14:23, шоты SC18/21/24/25 не получали план). Fix: нормализатор
    `normalizeShotId(shotId, episodeCode)` в `vgen-shot-helpers.ts` применяется ОДИН раз на
    единой входной двери — route `POST /api/episodes/[id]/trigger` (через неё идут ВСЕ
    диспатчи: инструменты Полины, tmp-скрипты, UI, будущий авто-EP). Короткий суффикс →
    полный id → дальше по пайплайну течёт только канонический. Идемпотентно (уже-полный и
    нераспознанная форма проходят без изменений). `getStoryboardShotById` оставлен СТРОГИМ
    намеренно — настоящая опечатка/несуществующий шот (SC28/31/32/36, которыми Полина
    холостила — см. gap #4) по-прежнему падает громко. **Урок для авто-EP:** короткий ключ —
    только для глаз (дисплей `shortShotLabel`), длинный — для адресации; конверсия один раз
    на входе, НЕ толерантность у каждого читателя (последнее размазало бы короткий ключ по
    событиям/именам/метаданным и заглушило бы опечатки).

11. **Ambient-самоподдержка Полины хлипкая.** Авто-реакция на фоновые `agent_completed`
    (завершение рендера) НЕ срабатывает надёжно — при сливе очереди Полина засыпает, нужен
    внешний «пульс» (Pascal-нудж). Прямые обращения (claude_message) теперь будят надёжно
    (gap #2 fix), а ambient — нет. **Fix:** либо чинить ambient-wake, либо авто-EP сам бьёт
    heartbeat-тик каждые N сек, пока очередь не пуста.

12. **Storyboarder был зашит на «ровно 3 акта» (источник E11 нумерации).** ✅ ПОЧИНЕНО
    2026-06-22 (q10a). Director спросил «почему нумерация поплыла только в E11?». Скан всех
    13 эпизодов: E01–E10 (+S14) — ВСЕ 3-актные (act-объектов=3, max A#=3, scriptActs=3,
    консистентно). **E11 — первый 4-актный сценарий за историю** (Завязка/Развитие/Кульминация/
    Развязка). Storyboarder (`storyboarder.ts`) хардкодил «Exactly THREE acts» в промпте,
    шаблоне (ACT 1/2/3) и постусловии (`acts.length !== 3`). LLM, увидев 4-актный сценарий, но
    под приказом «3 объекта», слил Акт 3+4 в один `act:3`, пометив финал shot_id `A4` →
    рассинхрон. Постусловие считало ТОЛЬКО число объектов (3==3 ✅), потому пропустило. Это
    нарушение skill-creation.md: контент (число актов = СЦЕНАРИЙ) зашит в процессный инструмент.
    **Fix:** число актов читается из сценария (`countScriptActs`, заголовки `## Act N`); промпт/
    шаблон/правило ведутся от него; постусловие — тройной инвариант `act-объекты == max(A#) в
    shot_id == scriptActs`, иначе HALT (ловит дрейф громко на генерации). Хелперы +
    `maxActInShotIds`, 7 юнит-тестов, контракт-yaml выровнен. **Урок для авто-EP:** любой
    «магический» структурный литерал (3 акта, N шотов, фикс. длительность) = латентный баг до
    первой структурной новизны; инвариант должен сверять ВСЕ представления (объект↔shot_id↔
    источник), а не одно. Остаток борда E11 (Акт4 под act:3) — правка после финала
    [[backlog_td_e11_board_act_grouping]] (q8b).

## ПРЕДЛОЖЕНИЯ по авто-EP
- EP владеет ЕДИНЫМ каноническим shot-list (полные ключи), сам детерминированно считает
  «недостающие», диспатчит по одному — не полагается на эвристику оператора «первый отсутствующий».
- Надёжный командный канал EP→оператор (mutation-authorized).
- Валидируемая математика длительностей (сумма = target, резерв под fade).
- Путь эскалации блокеров Директору (billing, regen-cap, ECONNRESET).

## РЕШЕНИЕ по архитектуре EP (Director q1, 2026-06-23)
- **НЕ строить Pascal вторым чат-LLM поверх Полины.** Анализ кода: у Pascal НЕТ своих
  инструментов — он только голос в team-chat, будит Полину; авто-реакция Полины read-only →
  команда Pascal не исполняется, только «озвучивается». Итог двух-LLM-цепочки = двойные
  токены + двоение актёров в феде (#7) + длинная ложная цепочка. Это аддитивная ловушка
  ([[anti_additivity_principle]]): ~80% функции EP уже в Полине (41 инструмент, режимная
  власть, work-plan ledger). Директор: «в принципе агент может решить эту задачу целиком».
- **Near-term:** голова = Тео/оркестратор (или один способный агент) через ОДНУ
  санкционированную дверь (`/api/episodes/[id]/trigger`, канон после normalizeShotId),
  Полина = руки. Цель авто-EP = свернуть голову в ПОВЫШЕННЫЙ РЕЖИМ оператора + код-цикл
  next-action (детерминированный, не сырой self-driving — harness его блокирует, #9), а НЕ
  второй мозг. Возможное тиерирование: управляющая модель на хорошем тире, воркеры на free.

## ГЛАВНАЯ ЦЕЛЬ (Director q1, 2026-06-23): система против выжигания токенов на НЕЭФФЕКТИВНОСТИ
Директор: жжём токены НЕ из-за супермоделей генерации, а из-за НАШИХ косяков — ошибки в
постановке задачи на генерацию ИЛИ в анализе → избыточные/повторные генерации. Симптом,
который он видит: несколько почти одинаковых видео-генераций подряд (повтор с тем же
провайдером/входом; регенерация, которой можно было не делать — отложить и решить потом).
**Нужен (это содержание блюпринта q13a):**
- детектор дубль-генераций (тот же shot + тот же провайдер + тот же промпт/входной хэш → стоп);
- гейт регенерации: не пускать повтор с идентичным входом без явного решения;
- «решить потом» как первоклассное состояние, а не немедленный регенерат;
- наблюдаемость потраченного на повторы (сколько токенов/$ ушло на дубли).
Связано с [[backlog_observability_failures_not_surfaced]], [[nudge_polina_dont_act_for_her]].
