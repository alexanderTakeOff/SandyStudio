# Почему выдача Sandy умерла с 01.08 — разбор до корня

**Дата:** 2026-08-13 · **Вопрос Директора:** «почему последние 0, а не 1400+»
**Ответ:** найден РЕАЛЬНЫЙ дефект — битый контейнер готового файла. Он объясняет часть смертей,
но **не все**: см. «Контрпример» ниже. Не контент, не метка, не unlisted, не made-for-kids.

## Прибор, который разделил

Порядок верхнеуровневых атомов ISO-BMFF в самом файле. `moov` — индекс: без него плеер
не может начать проигрывание, не скачав файл целиком.

```
E27, E28   старый конвейер   ftyp moov free mdat   ✅ впереди   →  700–1500 просмотров
E35 01.08  прямой прогон     ftyp free mdat moov   ❌ в конце   →  0
E36 04.08  прямой прогон     ftyp free mdat moov   ❌ в конце   →  0
S20-E06    11.08             ftyp free mdat moov   ❌ дефект был жив
S20-E07    13.08             ftyp free mdat moov   ❌ дефект был жив
```

YouTube помечает такие `nonStreamableMov` (`videos.list?part=suggestions`). Shorts-лента живёт
мгновенным стартом на свайпе — файл, который надо скачать целиком, она не раздаёт. Метка стоит
на **трёх** роликах канала: `46T4llGZibU` (E37), `iXlrtsPbpJg` (E35), `2luzZyG7_l4`.

## ЛОЖНЫЙ СЛЕД, которого чуть не хватило (та же дата, до заливки)

Первая версия этого разбора утверждала «5 из 5 без исключений», опираясь на признак
«`fileDetails.container = mov` + звуковая дорожка». **Признак оказался негодным: YouTube
вычищает `fileDetails` примерно через 12 суток.** Он делил каталог по ВОЗРАСТУ, а не по
битости — все живые ролики просто старше. Проверка, которая это вскрыла: тянуть поле не по
десяти подозреваемым, а по ВСЕМУ каталогу и смотреть, не совпадает ли наличие поля с датой.

## ВТОРОЙ ложный след — `embeddable=false` (та же дата, убит перепроверкой)

Флаг `status.embeddable=false` (вместе с `publicStatsViewable=false`) стоял ровно у шести
мёртвых роликов и ни у одного из десяти живых — и объяснял даже E33, который контейнером не
объясняется. Директор потребовал перепроверки. Две read-only проверки убили гипотезу:

1. **Даты.** E33 вышел 01.08 20:00 → через ~9 ч **1 просмотр** (здоровый сосед: **1269**).
   Первое касание статуса — **06.08 09:39**, через пять суток. Состояние раньше признака.
2. **Контрольная группа.** Тот же флаг у восьми `unlisted`-роликов от 10–19 июля, которые
   публичными не были никогда. Признак есть — состояния нет.

Механизм: `videos.update` с `part=status` заменяет объект целиком, непереданные булевы поля
обнуляются. Флаг метит КАСАНИЕ. Касали мы мёртвых — потому что они мёртвые. Обратная
причинность.

Остаточная задача (гигиена, не расследование): `embeddable=false` реально запрещает
встраивание. Заводить безопасный путь смены статуса — читать текущий `status`, менять одно
поле, писать целиком — рядом с `updateVideoMetadata` в `youtube.ts`, который решает ту же
задачу для `snippet`.

## Контрпример, который дефект НЕ объясняет

`G3I_kR-Y9Tk` — это **E33, собранный 29.07, до прямого прогона**. Файл на диске здоровый
(`ftyp moov free mdat`), метки `nonStreamableMov` нет. Ролик висел публично **одиннадцать
суток и дал 11 просмотров**. Соседний `SNqGFyUKYT0` (02.08, тот же слот 20:00Z) дал 1269 за
первые сутки.

Значит **второй дефект существует, он старше прямого прогона и НЕ найден.** Отдельная ветка
расследования; чинить контейнер всё равно надо, но объявлять причину закрытой нельзя.

Оговорка по E33: в медиа-кэше лежит только `v01-DRAFT`, а публиковался ассет `v01-APPROVED` —
теоретически на канал уехал другой файл. Проверить нечем, деталей площадка уже не хранит.

## Виновная строка

`webapp/scripts/run/stitch.ts:194` — сборщик прямого прогона:

```js
args.push('-c:v','libx264','-preset','medium','-crf','19','-pix_fmt','yuv420p','-r','24');
```

`-movflags +faststart` нет. Агентский сборщик (`ffmpeg-stitch.ts`) его ставил всегда.
Прямой прогон начался 31.07 — первый битый кат 01.08. День в день.

## Корень

**Закон вывода был продублирован в четырёх сборщиках.** Скрипт честно переиспользовал общие
`buildConcatList` и `buildMusicAudioFilter` — «как склеить» и «как звучать» жили в одном месте.
А «как замуксить» вынесено не было, и прямой путь собрал свой набор, потеряв единственный флаг,
от которого зависит раздача.

Второй корень: **у выходного файла не было приёмки.** Площадка сама сообщала `nonStreamableMov`
через API — мы это поле не читали. Отказ был молчаливым, и потому прожил 11 дней.

Третий, организационный: снимки канала не собирались 07–10.08, отчёты Head of Growth не строились
с 06.08. Обвал «1400 → 11» случился 01.08 и его никто не смотрел одиннадцать дней.

## Что сделано (13.08)

- `DELIVERY_MUX_ARGS` в `ffmpeg-stitch.ts` — один закон вывода на студию; три сборщика берут его
  вместо своих списков.
- `assertStreamableDelivery()` — приёмка после каждой сборки, отказ громкий с названной причиной.
- `__tests__/lib/delivery-mux-law.test.ts` — сторож читает ИСХОДНИК каждого производителя:
  свой `-movflags` = закон снова разошёлся. Старые тесты `+faststart` проверяли, но лишь у двух
  сборщиков из четырёх — сторож, покрывающий не все пути, ловит те, где ошибки и не было.

Проверка эффекта на живом битом файле: `ftyp free mdat moov` → `ftyp moov free mdat`.

## Эксперимент, который проверит гипотезу без ошибок

Заменить файл у опубликованного видео нельзя — только перезалив как новое и снятие старого.

**Один ролик, один регулятор.** Единственный чистый носитель дефекта — **`46T4llGZibU` (E37)**:
метка есть, файл на диске битый, и он висел публично шесть суток с тремя просмотрами. Остальные
не годятся: E35 был публичен около суток, `2luzZyG7_l4` не был публичен никогда, E33 здоров.

Условия: тот же контент, тот же слот 20:00Z, старый в `private`. Планка сравнения — `SNqGFyUKYT0`
(1269 за первые сутки). Заливка через API с `publishAt`: этим же способом уходил выстреливший
`SNqGFyUKYT0`, поэтому «API против руки» — не переменная (все 12 живых залиты API).
