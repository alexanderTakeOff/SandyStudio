## §2. `ss-series-starter` — скилл для Полины

**Актор:** Полина (EXEC-CONC), руки. **Триггер:** Директор говорит «начинаем новый сериал».

**Премисса:** сериал заводится под названного покупателя — канал или заказчика. Без него это
не сериал, а этюд.
**Опровергатель:** покупателя назвать некому → HALT, первый вывод роли — запрос доказательства,
а не работа. Владелец опровергателя — НЕ Полина (производитель не может быть своим скептиком).

**Что своё:** читает §1 как порядок; на каждом шаге либо исполняет, либо задаёт ОДИН вопрос
Директору. Гейты, которые не её: стиль-якорь, LOCK, деньги, публикация.

### Главная находка о Полине — 30.07, ради неё скилл и нужен

Её собственный предложенный порядок завода сериала **не содержал ни одного шага про визуальный
канон**: от общей идеи она шла прямо к сценаристу. Для сериала, у которого канон уже есть, это
верно. Для НОВОГО — это ровно тот canon-gap, на котором пайплайн потом встаёт на префлайте
референсов.

Отсюда назначение скилла: он существует не чтобы напомнить ей шаги, которые она знает, а чтобы
вставить блок, которого в её модели мира **нет вообще**. Это и есть проверяемая польза
артефакта: без скилла она уверенно и вежливо ведёт к дефекту.

**Открыто:** какой шаг §1 она физически может исполнить сама сегодня. Проверяется по ходу
прогона; всё, что не может — это разрыв в инструменте, и он идёт в
`docs/plans/showrunner-tooling-gaps.md`, а не в скилл.

## §3. `/ss-run` — скилл + тонкая слэш-команда для Тео

**Актор:** Тео, прогон **от имени Директора** с полными правами. **Управление — через Полину**,
а не своими скриптами: скрипт мимо приложения не оставляет следа ни в леджере, ни в матрице.

**Что своё:**
- заводит сериал **и** эпизод, ведёт по §1 до финалки;
- держит режим: канон-блок Mode 3 → Mode 1 перед `createEpisode`;
- Директора трогает только на хард-лимитах: деньги · видео · LOCK · публикация;
- пишет хронику и этот файл по ходу — иначе прогон не конвертируется в знание.

**Опровергатель — матрица состояний:** предусловия ячейки выполнены, а стадия не двигается →
порядок в §1 неверен, HALT. Машинное доказательство вместо мнения того, кто скилл написал.

**Открыто:** делится ли §1 на «завод сериала» и «завод эпизода» как два входа, или это один
проход. Решится, когда пройдём шаг 11 — раньше это угадывание.

## §4. РАЗВЕДКА штатного пути — 30.07 ≈15:10

**Главный вывод: нового кода не требуется ни строчки.** Весь путь завода канона уже в
приложении, и он уже мульти-референсный. Скрипты были не нужны — я почти написал 15-й.

| Что нужно | Чем делается | Замечание |
|---|---|---|
| создать ассет Библии | `POST /api/series/{id}/bible` | принимает `section`+`slug`+`content` **и сразу** `staging_path`/`drive_file_id` — то есть уже готовую картинку |
| нарисовать картинку ассета | `POST /api/series/{id}/bible/{assetId}/regenerate-image` | дефолтный провайдер — **`openai-edits-multi`**, референсы собираются из identity/location/style-якорей серии сами |
| закрыть канон | `POST /api/series/{id}/bible/{assetId}/lock` | `regenerate-image` отказывается работать по LOCKED — защита есть |
| руками положить готовый файл | `POST /api/assets/{id}/upload` | тоже отказывается по LOCKED |
| то же руками Полиной | инструмент `setBibleContent` | текст дословно, новая DRAFT-версия, старые остаются историей |

**Отсюда правило для обоих скиллов:** канон-ассет заводится через приложение, а не скриптом.
Скрипт не оставляет следа ни в леджере, ни в матрице состояний, ни в Drive-раскладке — а
`persistBinary` внутри маршрута делает канонические имена и заливку в Drive сам.

### Опасность, найденная тут же

Скилл `bible-asset-image-auto-gen` дорисовывает картинку сразу после того, как задан ТЕКСТ
ассета. Для двух УЖЕ утверждённых кадров это худший исход: заплатим второй раз и получим
ДРУГУЮ картинку вместо утверждённой. Значит на шаге 8 текст и картинка кладутся **одним**
вызовом (`bible` POST с `staging_path`), а не «текст, потом дорисовать».
