# D86 — карта конвейера в промпте ума

**Причина.** В `lib/mind/prompt.ts` нет ни одной станции: есть доктрина, девять правил и
контекст. У СТАРОГО консьержа карта была (`lib/concierge/system-prompt-builder.ts:103` —
brief / casting / writer / script-critic / storyboard / references со состояниями). Новый
промпт писался с нуля и её не перенёс — тот же класс, что D69 и D81.

**Как делать.** Блок строится **из** `ROW_DEFINITIONS` (`lib/api/pipeline-stages.ts:252`,
уже экспортирован), а не пересказом: второй список станций разойдётся с первым на первой же
правке конвейера. Там 23 станции с `phase` / `role` / `serves` / `agents`.

Карта обязана нести различие, которого ум сейчас не знает: часть станций — **вход Директора**
(`role: 'input'`, `agents: ['Director']`: канон серии, бриф, кастинг, музыка), а не работа
ума. Кастинг он не «пропустил» — он не знал, что его надо ЗАПРОСИТЬ. Критики (`role:
'critic'`, поле `serves`) обслуживают конкретного автора — это тоже видно из реестра.

Формулировка правила: маршрут существует, порядок не выбор ума; пропуск станции — осознанное
решение, объявленное вслух, а не умолчание. Опора — слова Директора на Ш0 прогона: «по
потоку студии, а не так, как нам хочется или более эффективно».

Блок кладётся в `stable`-часть промпта (кэшируется, от эпизода не зависит).

# D88 — прямой путь не умеет версионировать (НЕ ломать существующую архитектуру)

**Модель Директора, которая УЖЕ построена:** «Сгенерировали кадр. У него есть версия. Не
понравился — создаётся новая версия. И утверждается одна из них. Доступны все для просмотра.
У нас для этого есть целая архитектура в графическом интерфейсе, который мы очень долго
делали.» Проверено: **149 связок эпизод+кадр имеют по несколько строк**.

**Что выяснило исследование (файлы и правила — не догадки):**

- **Агентский конвейер ВСЕГДА вставляет новую строку**, номер `max(version)+1` по
  `(episode_id, file_type)` — `lib/agents/runner.ts:3511-3526`,
  `lib/agents/runners/episode-references.ts:2200-2209`, `:2619-2623`. В место никогда не
  пишет.
- **Прямой путь обновляет** строку по `(file_type, scope)` и при вставке хардкодит
  `version: 1` — `scripts/run/_asset.ts:71-119`, `:166`. Версий не бывает по конструкции.
- `--version` у `register-media` (`scripts/run/register-media.ts:22`) — **косметика имени**:
  переименовывает ту же строку и осиротит прежний файл в кэше.
- `write-asset.ts:37` обещает «новая версия заводит соседа, не затирает историю» — **это
  неправда** при нынешнем `persistAsset`.
- **Ключ идентичности везде — `metadata.shot_reference.shot_id`**, не `file_type`: так
  группирует кебаб (`components/animatic/AnimaticPlayer.tsx:472-490`), так работает
  инвариант (`lib/api/single-approved.ts:121-137`), так устроен индекс БД.
- «Активная» версия НЕ хранится, а **выводится**: `lib/api/timeline-cell-resolver.ts:147-152`
  — APPROVED/LOCKED=3, REVIEW=2, DRAFT=1, INVALIDATED=0; при равенстве — старше версия.
  Единственный переключатель — ✓ в кебабе → `POST /api/assets/[id]/approve` →
  `demoteSiblingApproved` уводит прежнюю в `INVALIDATED`.

**🔴 Мина, которую обязательно учесть.** `isShotReferenceV2` требует маркер
`contract: 'episode_references@v2'` (`lib/api/shot-reference.ts:371-376`), а прямой путь
пишет только `{ shot_id }` (`scripts/run/_asset.ts:279`). Значит `resolveSlotDescriptor`
возвращает `null` → **демоушен для прямых кадров не работает вовсе**, а частичный
UNIQUE-индекс `assets_one_approved_per_shot` (`0024_eref_one_approved_per_shot.sql:18-26`)
контракт не проверяет и сработает. Как только `persistAsset` вставит ВТОРУЮ APPROVED-строку
на тот же шот — Postgres откажет по duplicate key, и никто не понизит прежнюю. При этом
`gen-frame` умалчивает `status: APPROVED` (`gen-frame.ts:40-44`).

**Минимальная форма правки (без слома семи других инструментов):**
1. Опциональный флаг `newVersion` в `PersistAssetArgs` — прокинуть только из `gen-frame`;
   контракт идемпотентного обновления для остальных не трогать.
2. Номер — правилом конвейера `max(version)+1` (запрос уже есть в `_asset.ts:71-77`).
3. Имя файла пересобрать под новый `vNN` — этого требуют UNIQUE на `filename`
   (`0002_core_tables.sql:50`) и CHECK формата (`0017:20-23`, ровно две цифры).
4. **Новая версия рождается `REVIEW`, не APPROVED** — так делает и агентский конвейер
   (`episode-references.ts:2818`), и это единственный способ не упереться в индекс. Кадр всё
   равно виден: у REVIEW ранг 2. Утверждает Директор кебабом — ровно его модель.
5. Починить маркер: либо стампить `contract` в `shot_reference`, либо (меньше и безопаснее)
   в `resolveSlotDescriptor` ветку `IMG-episode_ref` перевести на `resolveShotId()`
   (`lib/api/shot-identity.ts:26-37`), который работает без контракта. Иначе аппрув упадёт.

**Чего НЕ делать:** не трогать индекс `assets_one_approved_per_shot` (его снятие уже
предлагалось и отклонено — `single-approved.ts:14-19`); не менять `file_type` прямого пути на
длинную агентскую форму — идентичность держится на `shot_id`.

# D89 — рецепт промпта сделан ЧЕТВЁРТОЙ формой вместо переиспользования

Вчерашняя правка D87 завела `metadata.recipe` — свой формат. Исследование показало, что в
студии уже есть **три** места, где живёт то же самое:

- `metadata.shot_reference.generation_history[]` — `GenerationAttempt`
  (`lib/api/shot-reference.ts:106-125`): версия, провайдер, модель, промпт, `references_used`,
  цена. **Полностью покрывает содержимое `recipe`.** Питает AttemptsStrip в дровере.
- `metadata.image_prompt` — то, что РЕНДЕРИТ дровер (`AssetImagePromptSection`). Минимальная
  рабочая форма показана у якорей: `episode-references.ts:1867-1885`.
- `SPC-ref_plan-<shot_id>` — отдельный ассет с промптом в fenced-json.

То есть промпт сохраняется (это хорошо и это закрыло залёт), но **не показывается**: моя
форма невидима существующему UI. Правка: писать `image_prompt.history[]` в той же форме, что
якоря (копипаст из `episode-references.ts:1872-1885`) — тогда дровер отрисует без единой
правки фронта. Дополнительно — запись в `generation_history[]` зажжёт AttemptsStrip.

Это мой собственный промах против anti-additivity: сделал новую сущность там, где было три
готовых.
